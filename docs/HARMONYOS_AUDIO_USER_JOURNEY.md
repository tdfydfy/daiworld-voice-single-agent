# HarmonyOS 音频用户旅程与业务逻辑

更新时间：2026-08-12

> 本文是 HarmonyOS 单 Agent 音频业务的权威入口。它只回答用户经历什么、业务如何转换、客户端与服务端分别保证什么。平台接口、音频资源和代码拆解属于下游设计，见[音频可靠性技术策略](HARMONYOS_AUDIO_STRATEGY.md)和[组件拆解参考](HARMONYOS_AUDIO_COMPONENT_DESIGN.md)。

## 1. 最终目的

产品要保证的不是某个录音或播放接口一直运行，而是一段连续、可干预、可恢复的对话：

> 用户说出的有效内容不丢失，Agent 已接受的任务不重复执行，已经产生的回复不无故跳过；亮屏、息屏、前台、后台和短暂故障不改变用户意图。

因此业务只保留一个循环：

```text
用户发起或补充对话
  -> 等待 Agent 反应
  -> 聆听播报
  -> 继续表达、补充任务或停止任务
  -> 回到下一轮
```

“补充任务”不是第五种场景，而是在等待或播报期间重新进入“用户表达”。“停止任务”是清空当前执行链的显式出口。“关闭话筒/打开话筒”只切换 ASR 结果的消息路由模式，不是对话阶段，也不等同于关闭/启动物理采集或识别。“退出软件”是结束本地运行的最终出口。

每次应用冷启动后，完整话筒链路默认未开启，必须由用户首次手动启动。启动后，物理采集和 ASR 都保持连续；日常的“关闭话筒/打开话筒”只在“普通对话模式”和“仅系统指令模式”之间切换，不重启采集或 ASR。

## 2. 四个用户环节

### 2.1 用户发起或补充对话

用户期待：开口后被持续听见；一句话确认完成后只提交一次；补充内容不会因为 Agent 正在思考或播报而丢失。

业务过程：

1. 话筒开启时持续收音，并把临时识别结果呈现为“正在听”。
2. 一句话形成最终文本后，先判断它是控制指令还是普通内容。
3. 普通内容被确认为一条用户输入。Agent 空闲时立即开始当前任务；Agent 忙碌时按顺序成为补充任务。
4. 如果用户在播报中开口，先暂停当前播报，完成本句话的识别与提交，再恢复未播完的原播报。
5. 只有服务端确认接受后，界面才能显示“已提交”或“已排队”；失败的内容保留为未提交，不能静默消失或假装成功。

仅系统指令模式下，ASR 仍形成识别结果，但普通语音不能进入本环节，也不能传给 Agent；只检查“停止任务”“打开话筒”“退出软件”三个精确系统指令。用户可用“打开话筒”或界面恢复普通对话模式，也可使用文字输入。应用本次运行尚未手动启动完整话筒链路时，不能进行任何后台采集或语音控制。

### 2.2 等待 Agent 反应

用户期待：明确知道任务已经被接受、Agent 正在处理；等待期间仍可补充；切到后台或息屏不会让同一任务重做或消失。

业务过程：

1. 当前 Agent 任务由服务端持有，客户端显示已接受、处理中、使用工具或等待审批等真实状态。
2. 话筒开启时继续收音，用户的新表达回到上一环节，并按服务端顺序排队。
3. 仅系统指令模式下仍持续识别，但普通结果只在本地丢弃，不生成对话气泡或 Prompt；当前 Agent 任务和播报继续。
4. Agent 产生可播报回复后进入“聆听播报”；若回复无需播报，则任务完成后直接回到可再次表达的状态。
5. 客户端断线后恢复同一会话并读取任务进展，不能为了“恢复”而再次提交原任务。

### 2.3 聆听播报

用户期待：回复按顺序完整播放；可以随时补充或停止；播报结束不自动关闭话筒。

业务过程：

1. 回复文本一经接受，就成为独立的待播内容；Agent 生成完成和设备实际播完是两件事。
2. 播报按已接受顺序进行，不因新回复到达、亮屏/息屏或前后台变化而跳过当前内容。
3. 用户真实开口时暂停当前播报，以便优先听清用户；普通补充提交后恢复原播报。
4. 设备无法确认精确播放位置时，从最近一个可靠的短段检查点恢复。允许有限重复，不允许猜测进度后吞字。
5. 播报完成后：没有后续任务则等待用户下一次表达；已有补充任务正在处理则回到“等待 Agent”；已有下一条回复则继续播报。

### 2.4 停止或补充任务

这是用户在“等待 Agent”或“聆听播报”期间的干预，不是另一套流程。

| 用户动作 | 当前任务 | 当前播报 | 话筒 | 后续去向 |
| --- | --- | --- | --- | --- |
| 普通补充 | 继续执行，补充按顺序进入 Agent | 用户说话时暂停，补充提交后恢复 | 保持开启 | Agent 按任务顺序处理；与旧播报何时播完相互独立 |
| `停止任务` | 终止当前任务并取消全部排队任务 | 立即停止当前播报、重读和全部待播内容 | 保持当前消息路由模式 | 任务链清空后回到可发起下一轮 |
| `关闭话筒` | 不受影响 | 不受影响；若因识别指令而临时暂停，执行后恢复 | 采集和ASR继续，切为仅系统指令模式 | 当前任务/播报继续；普通语音不传 Agent |
| `打开话筒` | 不受影响 | 不受影响 | 采集和ASR不重启，恢复普通对话模式 | 无需操作屏幕即可恢复普通对话 |
| `退出软件` | 默认不主动中断远端任务 | 立即停止所有本地输出 | 终止采集和ASR | 断开连接、释放后台资源并关闭应用 |

普通故障和断线恢复不能静默删除已接受的补充内容；但用户明确执行“停止任务”时，当前任务及全部排队补充都必须取消。这是该指令的既定含义，不再保留队列，也不得在恢复连接后自行重提。

## 3. 四个系统指令

### `停止任务`

- 取代宽泛的“停止”作为目标中文语音控制词。
- 只在整句最终识别结果与控制词一致时执行；“不要停止任务”“停止任务以后再……”等包含其他语义的句子按普通内容处理。
- 一次性停止当前流式播报、历史重读、全部待播内容和思考呼吸音，再请求服务端执行等价于 Hermes `/stop` 的中断：终止正在思考/执行的任务并取消全部排队任务。
- 服务端结果未确认时明确显示“正在停止”或“停止状态待确认”；确认后播放一次停止提示音。恢复连接时不得重提被取消的任务。
- 不改变完整话筒链路、ASR 或消息路由模式。仅系统指令模式下也必须能够执行。无当前/排队任务且无播报时不创建新任务，只反馈当前没有可停止的内容。
- 界面停止按钮与语音指令具有相同语义，并作为识别失败时的可靠入口。

### `关闭话筒`

- 目标语义是切换为“仅系统指令模式”，不是关闭物理麦克风或 ASR。采集、识别和收句持续运行，但普通识别结果不创建用户消息、不播放收到提示音、不进入 `prompt.submit`。
- 该模式只允许三个精确整句系统指令：`停止任务`、`打开话筒`、`退出软件`。其他所有识别结果在本地丢弃，不发送到 Adapter、Hermes 或其他远端服务作意图判断。
- 不中断 Agent，不清空播报，也不关闭网络会话。界面必须明确显示“仅响应系统指令”，不能用“麦克风已关闭”暗示设备不再采集或识别。

### `打开话筒`

- 新增目标功能：在完整话筒链路已经由用户手动启动后，将消息路由从“仅系统指令”恢复为“普通对话”；采集和 ASR 始终是原实例，不重启。
- 由持续工作的 ASR 在本地系统指令门中识别；成功后恢复普通用户消息、收到提示音和 Prompt 提交，减少亮屏和屏幕操作。
- 每次应用冷启动的首次完整链路启动仍必须由用户在界面手动完成。“打开话筒”不得绕过首次权限授权、用户启动动作或系统级隐私指示。

### `退出软件`

- 仅在完整话筒链路已经启动、且整句最终识别结果精确匹配时执行；普通语句中的“退出软件”不触发。
- 立即停止正文、重读、提醒音、物理采集和 ASR，关闭语音及 Gateway 连接，释放 AudioSession、后台持续任务、定时器和内存队列，然后终止应用的本地运行。
- 默认不把“退出软件”扩大为“停止任务”：已经提交给 Hermes 的远端任务可继续，下次恢复同一会话时取得结果。用户要同时终止远端任务，应先执行“停止任务”，再退出软件。
- 退出后不自动重连或后台自启；下次打开应用仍需用户手动启动完整话筒链路。

当前实现仍接受“停止/stop”，且“关闭话筒”会停止 `AudioCapturer`；“打开话筒”和“退出软件”语音指令尚未实现。上述四项是目标业务语义，本轮文档不宣称代码已经生效。

## 4. 音频提醒

音频提醒是既有产品能力，属于对话状态反馈，不能在录播可靠性重构中遗漏：

| 提醒 | 触发条件 | 必须停止的条件 | 业务含义 |
| --- | --- | --- | --- |
| 收到提示音 | 一句话完成，且系统已经确认有效收句/接受输入 | 只播放一次 | 用户可以停止讲话，内容已经收到 |
| 思考呼吸音 | Agent 正在思考/执行，且当前无用户讲话、无正文播报、无更高优先级提醒 | 用户开口、正文开始、任务结束、停止、错误、审批/澄清出现 | Agent 仍在工作，不代表任务完成 |
| 停止提示音 | 停止动作已完成本地清理，并得到服务端停止确认 | 只播放一次 | 当前任务链和排队任务已经停止 |
| 错误警示音 | 出现新的、需要用户知晓且影响当前交互的错误 | 同一错误不重复轰炸 | 当前环节失败或需要用户处理 |

“系统确认收音”至少意味着已经形成有效完整话语，并进入可提交/已接受状态；纯噪声、空 final、被回音过滤的内容不能播放收到提示音。若服务端提交尚未确认，界面仍需区分“已收句”和“已提交”，提示音不能掩盖提交失败。

所有可听内容必须由同一个输出仲裁器串行控制，不能让多个播放器同时抢占：

```text
停止/错误警示
  > 用户讲话导致的立即静默
  > 正文播报（新回复和历史重读共用）
  > 收到提示音
  > 思考呼吸音
```

- 正文开始前，正在发出的短提示音可以有限排空；思考呼吸音必须立即让路。
- 收到提示音不得切断正文；正文正在播放时，将提示音放到最近的安全边界或省略，不能制造破音。
- 停止任务先清理正文、重读、待播和呼吸音，再播放停止提示；错误警示也不得与正文叠放。
- 提示音只表达状态，不改变 Agent、ASR、播报队列或话筒链路的业务状态。

## 5. 正交状态，不再扩展场景

四个用户环节是业务主轴。其他变化只用下面四组状态描述：

| 状态轴 | 取值 | 它决定什么 | 它不决定什么 |
| --- | --- | --- | --- |
| 完整话筒链路 | 本次运行未启动 / 已手动启动 / 正在退出 | 是否允许物理采集、ASR和系统语音指令 | 当前 Agent 是否继续 |
| ASR消息路由 | 普通对话 / 仅系统指令 | 识别结果能否成为用户消息并提交 Agent | 物理采集和ASR是否继续、Agent/播报是否继续 |
| 播报需求 | 无 / 待播 / 播放 / 因用户说话暂停 | 是否保留待播内容和播放资源 | 话筒是否开启、Agent 是否完成 |
| 运行环境 | 前台或后台；亮屏或息屏 | UI 是否可见、系统如何保障持续资源 | 对话阶段、任务语义、控制语义 |

Agent 任务状态由服务端独立持有，不与上述四轴合并。资源需求可以直接由事实推导：

```text
需要物理采集 = 完整话筒链路已手动启动
需要持续识别 = 需要物理采集
允许提交普通消息 = 需要持续识别 且 ASR消息路由=普通对话
需要保留播放 = 存在待播、播放中或因用户说话暂停的内容
需要持续音频保障 = 需要物理采集 或 需要保留播放 或 提醒音活跃
```

这些判断在亮屏、息屏、前台和后台完全相同。环境变化不能自动提交内容、停止任务、暂停 ASR、清空播报或重建仍然健康的资源。

## 6. 各环节叠加亮屏、息屏和前后台

| 用户环节 | 客户端必须保持 | 服务端必须保持 | 息屏/后台发生时 |
| --- | --- | --- | --- |
| 发起或补充 | 完整链路启动后持续采集和识别；普通对话模式维护未确认内容和提交状态 | 对输入只接受一次并返回明确结果 | 继续同一采集、ASR 和提交逻辑，不另建息屏识别路径 |
| 等待 Agent | 会话身份、任务展示；采集/ASR持续；普通模式接受补充；思考空窗播放呼吸音 | 当前任务、进度和已排队补充 | 任务继续；客户端恢复后读取进展，不重交任务或重启健康输入 |
| 聆听播报 | 统一输出顺序、当前位置检查点和待播内容；ASR持续监听 | 回复文本和任务结果可重新取得 | 继续同一输出队列，不根据屏幕状态猜测播放进度或切换播放器 |
| 停止或补充 | 控制动作立即可见，保留未确认状态 | 有序接收补充，确认当前任务中断结果 | 语音指令已被收取后照常完成；仅 UI 可见性变化 |

应用回到前台或屏幕重新点亮时，只做状态对账和界面刷新：读取话筒真实状态、当前任务、待播队列和播放健康；不重放 Prompt，不重置正常的收音或播放，不凭界面旧快照覆盖真实状态。

## 7. 前端、服务端与运行保障的职责

为避免按页面或 API 拆出第二套业务，逻辑组件只保留五个责任域：

| 责任域 | 持有的事实 | 核心逻辑 | 禁止承担 |
| --- | --- | --- | --- |
| 对话协调 | 当前处于表达、等待、播报或干预 | 根据已确认事件切换环节，协调“说话暂停、提交后续播” | 直接猜测平台录音/播放健康 |
| 输入 | 完整链路是否启动、真实采集/ASR健康、消息路由模式、当前识别文本 | 持续采集、识别和收句；先过本地系统指令门，再按模式决定普通结果是否提交 | 因亮屏/息屏换路径，把仅指令模式的普通内容发往远端，中断 Agent或清空输出 |
| Agent 任务 | 会话、当前任务、已接受补充、服务端确认状态 | 提交一次、按序排队；停止任务时原子取消当前和全部排队任务；断线恢复同一任务 | 控制设备采集或判断实际播完 |
| 可听输出 | 正文/重读/提醒的唯一队列、当前可靠检查点和优先级 | 统一分段、播放、提示音仲裁、因用户说话暂停、停止任务时清空 | 启停采集、把“生成完成”当成“播放完成” |
| 持续运行与恢复 | 采集/播放的真实健康、运行环境、恢复次数 | 由实际音频需求提供统一保障，只恢复失效的输入或输出管线 | 改变用户意图、业务环节或重提 Agent 任务 |

产品前端负责对话协调、设备输入输出、真实状态呈现和可恢复的本地队列。Adapter 只负责可靠传输和鉴权，不解释“停止/补充”的业务含义。Agent 服务端是会话、任务、排队和任务结果的权威来源，并保证断线后可恢复进展。

两条结构性约束必须长期保持：

1. **统一输入管线**：完整链路启动后只有一个持续 Capturer 和一条持续 ASR 链。亮屏/息屏、本地/远端后端、普通对话/仅系统指令模式不得通过停止采集或识别制造断点；同一句话跨识别 Session 轮换、短暂中断或前后台变化时仍按一个收句缓冲合并，避免被拆成多条提交。
2. **统一可听输出管线**：新消息流式播报、旧消息重读、协议播报和四类提醒都进入同一个调度器，复用同一分段、播放状态、代际隔离和设备输出；不允许各自持有可并发抢占的播放器或亮屏/息屏路径。

## 8. 状态切换总表

| 当前环节 | 事件 | 必须发生 | 下一环节 |
| --- | --- | --- | --- |
| 可表达/表达中 | 普通 final 被服务端接受 | 输入只提交一次，创建或排队任务 | 等待 Agent |
| 等待 Agent | 用户普通补充 | 补充被接受并保持顺序，当前任务不被误停 | 等待 Agent |
| 等待 Agent | 回复可播 | 建立待播内容，不改变话筒 | 聆听播报 |
| 聆听播报 | 用户开口并提交普通补充 | 暂停播报、提交补充、恢复原播报 | 聆听播报 |
| 聆听播报 | 当前播完且 Agent/队列仍有后续 | 按真实任务或队列状态继续 | 等待 Agent 或继续播报 |
| 等待/播报 | `停止任务` | 停当前及全部待播输出，取消当前和全部排队任务；输入模式不变 | 可表达或停止状态待确认 |
| 任意环节 | `关闭话筒` | 采集/ASR保持，切为仅系统指令；任务和播报不变 | 原环节 |
| 仅系统指令 | `打开话筒`或界面恢复 | 采集/ASR不重启，恢复普通消息提交 | 回到原对话环节并可表达 |
| 任意环节 | `退出软件` | 停止并释放全部本地音频、连接和后台资源；默认不停止远端任务 | 应用结束 |
| 任意环节 | 亮屏/息屏、前台/后台变化 | 只更新运行保障和 UI 可见性 | 原环节 |

## 9. 错误应对

错误不再按“息屏播放失败”“后台录音失败”等组合命名，而是按被破坏的承诺归类：

| 错误域 | 保留什么 | 自动恢复什么 | 恢复失败后 |
| --- | --- | --- | --- |
| 物理采集 | 已确认文本、完整链路启动意图、消息路由模式；未完成文本标为未提交 | 只恢复统一 Capturer，有限重试；不按屏幕状态换路径 | 明确显示输入不可用，提供文字输入/重新手动启动入口 |
| ASR/收句 | 物理采集、当前有效文本和消息路由模式 | 只恢复同一识别链，并用统一缓冲合并连续结果 | 显示识别和系统语音指令均不可用；不提交残缺重复内容 |
| 提交/连接 | 原输入、会话身份、服务端已确认状态 | 恢复同一会话并查询结果，不重复提交 | 保留为未提交或状态待确认，允许用户重试 |
| Agent 任务 | 已接受输入、已有进度和结果 | 由服务端继续或明确失败 | 结束本次任务并说明失败，话筒和已有播报不被连带关闭 |
| 播报 | 完整回复文本、待播顺序、可靠短段检查点 | 只恢复播放，从可靠检查点有限重试 | 保留文字结果并显示播报失败，不吞字、不影响 Agent 和话筒 |
| `停止任务` | 完整话筒链路和消息路由模式、已确认对话记录 | 本地所有输出先停，服务端 `/stop` 语义有限重试/查询 | 显示“本地已停止，任务/队列状态待确认”，不能声称服务端已全部取消 |
| `关闭/打开话筒` | Agent 任务、播报、物理采集、ASR和会话 | 只重试本地消息路由切换 | 保留请求状态并明确失败，不启停采集/ASR或影响任务 |
| `退出软件` | 已确认记录和远端任务身份 | 本地资源按统一释放顺序关闭 | 即使局部释放报错也继续关闭其余本地资源，并记录下次启动诊断；不得残留自动重连 |
| 可听输出冲突 | 完整正文、重读来源、提醒事件和可靠检查点 | 由唯一仲裁器停止低优先级输出并从安全边界继续 | 保留文字结果，明确播报失败；禁止并发播放、破音或吞字 |

统一恢复顺序是：确认用户意图未变 -> 判断哪个责任域真实失效 -> 只恢复该域 -> 与服务端/平台对账 -> 成功后继续原环节。恢复次数必须有限；耗尽后进入明确失败状态，不能无限重试或伪装正常。

## 10. 业务验收基准

1. 同一句普通输入最多被 Agent 接受一次；断线恢复不会重做任务。
2. 等待和播报期间都能补充，补充不隐式停止当前任务。
3. 用户说话只暂停播报；普通补充提交后原播报继续。
4. 有效收句后只响一次收到提示；思考呼吸音只在无人声、无正文播报的思考空窗出现；停止和新错误各有对应提示且不与正文打架。
5. `停止任务`停止当前/待播输出、当前 Agent 任务和全部排队任务，但不改变完整话筒链路、ASR或消息路由模式。
6. `关闭话筒`只切到系统指令模式，采集和ASR继续；仅能执行停止任务、打开话筒、退出软件。`打开话筒`只恢复普通消息提交。每次冷启动首次完整链路仍需手动开启。
7. `退出软件`释放全部本地音频、后台任务和网络连接并结束应用；默认不隐式停止远端 Agent 任务。
8. 新回复、历史重读和提醒由同一个输出调度器管理；持续采集、识别和两种消息路由模式由同一个输入管线管理。
9. 亮屏/息屏、前台/后台切换不改变上述业务语义，也不切换输入/输出路径。
10. 任一局部故障只影响对应责任域；无法恢复时明确失败，并保留已经确认的数据。
