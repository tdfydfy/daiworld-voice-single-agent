# 关键决策记录

## 2026-08-13 - 恢复 CoreSpeech 原生播放与专用后台模式

- 背景：`1.2.4` 已显式请求 `audioType: pcm`，但目标真机仍未产生任何 `SpeakListener.onData`；应用只能报“本地 TTS 未返回 PCM 音频流”。Git 历史同时证明 `1.1.2/1.2.1` 使用系统 `engine.speak()` 和播放优先的专用 `AUDIO_PLAYBACK` 时，用户曾确认息屏长文连续。
- 决策：本地 CoreSpeech 恢复系统内置播放器，不再要求 PCM 回调；后台任务按当前活动在 `AUDIO_PLAYBACK` 与 `AUDIO_RECORDING` 间切换，系统 TTS 启动前必须等待播放模式 ready，播放结束或用户开口后恢复录音模式。远端 TTS 继续使用应用 PCM renderer。
- 依据：目标设备的真实回调行为优先于 API 形式上的可选参数；组合后台任务虽保持存活，却没有阻止 CoreSpeech 在 `OnPageHide` 停止。旧版代码和真机验收提供了可复现的回退基线。
- 影响：撤销 `1.2.3/1.2.4` 的本地 PCM 格式、序号和无数据超时逻辑；保留 request generation、重复停止幂等、短段队列、采集恢复和系统设备选择。
- 重新评估条件：HarmonyOS 后续版本在目标设备稳定返回本地 TTS PCM，或专用后台模式经真机复验仍无法保持系统播放器。
- 来源：[用户真机反馈](plans/2026-08-13-audio-output-and-screen-off-followup.md)

## 2026-08-13 - CoreSpeech 只合成 PCM，应用确认真实播放完成（已由上方决策取代）

- 背景：系统 TTS 原生发声在播放中息屏时多次出现中断、卡顿或跳字；切到应用 PCM 后，旧实现仍用 JS 写回调和最后一包时长估算完成，并可能在息屏调度暂停时误判 renderer 卡死后重建，丢掉系统缓冲中尚未听到的几个字。
- 决策：CoreSpeech 本地 TTS 只通过 `SpeakListener.onData` 提供 PCM；应用按 `sequence` 排序去重并统一交给通信场景 `PcmPlayer`。合成完成不等于播放完成，只有 `AudioRenderer.drain()` 成功才结束当前段；看门狗以硬件 `framePos` 为健康证据，AudioSession 恢复优先保留 renderer，确需重建时回放最后一个未确认 PCM 缓冲。
- 依据：API 24 提供连续 PCM 序号、硬件播放时间戳和 renderer `drain()`；这些证据比屏幕事件、JS 回调间隔和时长估算更接近用户实际听到的进度。用户接受有限重复的风险边界优于跳字。
- 影响：本地 TTS 和远端 TTS 共用应用通信 renderer 与系统通信路由；停止、重播和迟到回调必须保持 request/generation 隔离。真机仍需确认息屏调度和具体设备驱动是否遵守 `drain()` 契约。
- 重新评估条件：目标设备返回非 PCM 或不连续分片、`drain()` 在真机上无法可靠完成，或回放检查点导致不可接受的重复；届时以完整短段重播或系统支持的持久播放器作为降级，不恢复按时长猜测完成。
- 来源：[用户真机反馈](plans/2026-08-13-audio-output-and-screen-off-followup.md)

## 2026-08-13 - 输出默认路由与用户自由选择分离

- 背景：真机已确认耳机插拔的系统默认路由正常，但用户明确要求任何时候都不能禁用播放器输出选择；默认设备只表示自动选择，不代表锁定设备。
- 决策：输出按钮在会话加载、播放和耳机接入等状态下始终可用，优先打开 HarmonyOS `voice_call` 原生设备选择面板，由系统展示当前可用的耳机、听筒和扬声器。系统面板调用失败时才回退到 `setCommunicationDevice(SPEAKER, true/false)`；附件拓扑改变时恢复系统首选，用户随后仍可手动覆盖。
- 依据：HarmonyOS 对附件枚举、可用性和通信路由拥有更完整的系统状态；应用只维护默认偏好容易与耳机热插拔及实际路由冲突。默认与手动选择分离也符合用户对可控性的明确要求。
- 影响：UI 不得按 `headsetOutputAvailable`、会话加载或播放状态禁用输出入口；应用不再叠加 `setDefaultOutputDevice`，实际设备标签由系统首选输出事件回写。
- 重新评估条件：目标系统不提供可用的 `voice_call` 设备面板，或真机证明面板无法覆盖通信 PCM renderer；届时保留始终可用的应用内三设备选择器，并继续以系统实际路由为权威状态。
- 来源：[用户真机反馈与输出选择要求](plans/2026-08-13-audio-output-and-screen-off-followup.md)

## 2026-08-12 - 关闭话筒切换消息路由，退出软件才释放完整链路

- 背景：原设计把“关闭话筒”理解为停止采集，随后一度修订为保留采集但暂停 ASR；用户最终明确要求采集与 ASR 都持续工作，以便在低操作模式下仍识别系统指令，并新增“退出软件”作为完整资源释放动作。
- 决策：每次冷启动首次完整话筒链路必须由用户手动开启。开启后，`关闭话筒`只把 ASR final 路由切到本地系统指令门，普通内容不建消息、不响收到提示、不进入 Agent；仅允许精确执行“停止任务”“打开话筒”“退出软件”。`打开话筒`恢复普通对话路由，不重启 Capturer 或ASR。`退出软件`停止并释放全部本地音频、后台任务和网络连接后终止应用，默认不隐式停止远端 Agent 任务。
- 依据：系统指令必须在无需操作屏幕时仍可用；停止采集或ASR会让语音恢复和退出失去入口，而把普通内容继续传到 Agent 又违背“关闭话筒”的用户预期。退出是资源生命周期动作，与停止远端任务应保持最小作用域。
- 影响：本决策取代本文件中“关闭话筒只停止真实收音”的旧影响结论。输入组件需要分离 `captureChainStarted` 与 `inputRouting`，系统指令门必须完全在客户端判定；当前代码尚未实现该语义。
- 重新评估条件：系统权限或审核规则不允许用户启动后持续识别，或用户要求“关闭话筒”具备严格隐私停采语义；届时必须改名或提供独立“停止监听/退出软件”，不能用错误 UI 文案掩盖真实采集。

## 2026-08-12 - 停止任务等价于 Hermes `/stop`

- 背景：此前把停止任务只理解为中断当前 Agent turn，并对已排队补充做状态对账；用户明确纠正为 `/stop` 语义。
- 决策：精确“停止任务”和界面停止按钮必须原子停止当前正文/重读/待播/思考提醒，终止当前 Agent 任务并取消全部排队任务；输入链路和消息路由模式保持。服务端确认完成后只播放一次停止提示，迟到事件不得恢复被取消的任务或输出。
- 依据：用户需要一个可以把整个当前执行链归零的确定动作，保留排队任务会产生停止后继续工作的反直觉行为。
- 影响：需要确认 `session.interrupt` 是否完整实现 `/stop` 队列清理，否则扩展 Runtime 协议或使用 Hermes 正式等价能力；恢复连接不得重提被取消 Prompt。
- 重新评估条件：Hermes `/stop` 语义发生变化，或产品未来需要“只停止当前任务但保留排队”的独立动作；届时使用不同名称，不能弱化“停止任务”。

## 2026-08-12 - 正文、重读和提醒使用唯一可听输出仲裁

- 背景：已有收到、思考呼吸、停止和错误提示音，但历史上出现播放队列竞争、提醒与朗读抢占、新消息流式播报和旧消息重读路径分叉、分段破音及屏幕状态改变路径。
- 决策：新消息、历史重读、协议播报和四类提醒全部进入同一个输出协调器；统一优先级为停止/错误警示 > 用户讲话静默 > 正文/重读 > 收到提示 > 思考呼吸。任一时刻只有一个可听输出所有者，亮屏/息屏不改变分段、队列或播放器。
- 依据：所有声音最终竞争同一个物理输出，分散播放器无法可靠表达抢占、排空和恢复顺序。
- 影响：`AudioCuePlayer`降为窄执行器，不能与正文并发；收到提示只在有效收句/接受后一次性触发，呼吸音只在无人声无正文的思考空窗出现，停止确认和新错误各播放对应提示。
- 重新评估条件：系统提供可证明无焦点冲突的独立混音通道且产品明确需要叠加声音；即便如此，业务优先级和代际隔离仍保留。

## 2026-08-12 - 音频业务以用户旅程为主轴

- 背景：按录音、播放、等待、亮屏、息屏、前台、后台及其组合枚举场景，产生了大量编号和组件调用链，掩盖了用户实际经历的同一个对话循环。
- 决策：业务只按“发起或补充对话 -> 等待 Agent -> 聆听播报 -> 停止或补充任务”分类。话筒意图、播报需求以及亮屏/息屏和应用前后台是覆盖主流程的正交状态，不扩展为新的业务场景；代码组件先按输入、Agent 任务、播报和持续运行的独立事实所有权拆解。
- 依据：用户目的和控制语义在运行环境变化前后不变；把环境条件与业务阶段混成一个枚举会产生组合爆炸，也容易形成亮屏/息屏两套逻辑。
- 影响：[音频用户旅程](HARMONYOS_AUDIO_USER_JOURNEY.md)成为业务权威入口；策略和组件蓝图降为下游技术参考，`S00-S21` 只表示测试或故障序列。
- 重新评估条件：产品出现无法归入该循环的独立用户目标，而不是现有环节的环境变化或异常分支。

## 2026-08-12 - 中文停止控制词收紧为“停止任务”

- 背景：单独使用“停止”语义过宽，既容易与普通表达混淆，也可能因短词识别不稳定而难以触发；同时“停止任务”和“关闭话筒”的作用域需要对用户明确。
- 决策：目标中文控制词使用整句“停止任务”，只中断当前 Agent 任务和属于它的播报，不改变话筒状态；“关闭话筒”只停止真实收音，不影响 Agent 或播报。包含其他语义的句子不触发控制，界面按钮提供同义可靠入口。
- 依据：控制词应包含被操作对象，破坏性动作应精确匹配并保持最小作用域。
- 影响：当前 `停止/stop` 代码仍待后续迁移；迁移完成前文档必须区分目标业务语义与已实现行为。
- 重新评估条件：真机 ASR 证据表明“停止任务”仍无法可靠识别，或产品需要兼容其他语言；届时调整明确短语或交互确认，不退回模糊子串匹配。

## 2026-08-12 - 音频后台保护由录播切换改为组合租约（已由 2026-08-13 决策取代）

- 背景：此前为解决纯 `AUDIO_RECORDING` 无法保障息屏 TTS 的问题，采用播报窗口切到 `AUDIO_PLAYBACK`、播完恢复录音的策略；`1.2.1` 真机再次复现息屏播放中断、卡顿、吞字和录音中断，且代码确认切换过程是异步 stop/start。旧决策的重新评估条件已经满足。
- 决策：只要存在录音或播放需求，就持有一个同时声明 `audioRecording` 和 `audioPlayback` 的组合后台租约；亮屏、息屏和录播活动变化不触发模式切换。AudioCapturer 和首段 TTS 必须等待租约 ready，真实健康由平台状态、PCM 心跳和播放进度分别确认。
- 依据：屏幕状态只改变系统调度环境，不改变用户意图；录音与播放可同时存在，使用互斥优先级无法完整表达需求；异步 stop/start 会制造后台保护空窗。完整推导见[HarmonyOS 音频策略](HARMONYOS_AUDIO_STRATEGY.md)。
- 影响：`BackgroundAudioTaskOwner` 需要组合模式和可等待的 ready 状态，`SingleAgentController` 不再选择 recording/playback 优先级；旧的“后台任务以实际播报窗口优先”保留为历史记录，但不再是现行目标架构。
- 假设：目标 API 24 和真机允许 UIAbility 同时申请两种已在清单声明的后台模式。
- 重新评估条件：目标真机明确拒绝组合模式，或 SDK 行为证明组合租约不能同时保护采集和播放；届时优先验证原地更新能力，最后才采用可等待、无空窗且有故障状态的串行切换降级方案。

## 2026-08-12 - Provider 模型目录由 Hermes 配置显式补充

- 背景：默认 Provider 能发现完整模型目录，而备用 Provider 只返回各自 `default_model`，导致客户端模型选择项不完整。
- 决策：模型可选范围以 Hermes `providers.<provider>.models` 为显式目录；当上游 `/models` 返回不完整或不稳定时，配置 `discover_models: false`，让选择器只使用手工列表。`default_model` 只负责默认值；`model.aliases` / `model_aliases` 只负责快捷别名，不作为多个 Provider 共用的目录来源。
- 依据：Hermes `/api/model/options` 会透传规范化后的 Provider 模型列表，HarmonyOS 已在真机验证手工配置后的 drag / wawapi 模型可以选择和切换。
- 影响：模型目录保持服务端单一权威来源，客户端不写死供应商或模型；列表中出现模型不代表上游一定支持该模型 ID，仍需以实际调用结果为准。
- 重新评估条件：Hermes 配置格式或 `/api/model/options` 契约发生变化，或供应商开始提供完整可靠的模型发现接口。

## 2026-08-12 - 系统 TTS 按文本统一分段，不按来源或屏幕状态分叉

- 背景：历史重读一次性提交完整文本，旧的最终余段快捷路径曾产生 254 字长段；新消息则逐步流入。同一系统 TTS 在播放中途息屏时可能吞掉当前缓冲的一部分，却仍报告正常完成。
- 决策：新消息和历史重读只保留输入到达方式的差异，进入 `SystemSpeechQueue` 后统一使用同一套句边界、首段、续段、尾段和硬上限规则；亮屏/息屏不参与业务分支，也不通过屏幕事件猜测系统真实播放进度。
- 依据：消息来源和屏幕状态不应改变文本播报语义；公共尾段上限能消除历史重读的超长余段，并把平台切换异常限制在较短完整句内。
- 影响：系统 TTS 队列不包含 replay/screen 模式；首段保持 20–48 字快速起播，后续段优先约 40–80 字且不超过 96 字。流式文本可能比以前更频繁调用系统 TTS，真机需同时验收衔接和自然停顿。
- 重新评估条件：若统一短分段仍无法避免明显吞音，则验证系统 TTS 是否支持可靠的仅合成 PCM 模式并由应用自管播放；在取得真实播放进度前，不实现息屏事件强制续播。

## 2026-08-12 - 后台任务以实际播报窗口优先

- 背景：持续开麦时旧逻辑始终持有 `AUDIO_RECORDING` 长时任务，即使系统 TTS 已排队或播放；真机表现为亮屏长文正常、息屏出现断连、缺字漏字和破音。
- 决策：TTS 处于 `queued/playing` 或系统回调确认正在播报时，后台任务切换为 `AUDIO_PLAYBACK`；播完或用户真实开口进入暂停态后恢复 `AUDIO_RECORDING`。后台意图切换不主动停止麦克风采集。
- 依据：输入采集与后台运行意图是正交状态；息屏时后台模式应描述当前最需要系统保障的实际音频活动。
- 影响：开麦和播报并存时播放获得息屏优先保障，用户开口后录音立即恢复优先；后台任务切换日志可用于真机确认事件顺序。
- 重新评估条件：HarmonyOS 后续支持同时声明录音与播放长时任务，或真机日志证明模式切换会中断采集、引入更严重的音频抖动。

## 2026-08-12 - HarmonyOS 保持为有限模块的 Hermes 薄客户端

- 背景：客户端的产品职责是接入后端 Hermes Agent，并提供鉴权、设置、输入、输出和状态展示；当前多个职责集中在超大控制器中，但拆解本身也可能产生新的复杂度。
- 决策：保留一个面向 UI 的薄控制器作为门面和少量跨域协调点，内部只形成设置/鉴权、Hermes 运行、语音输入、语音输出、对话状态五个责任域；不引入事件总线、通用依赖注入、重复仓储/用例层或按方法机械建模块。
- 依据：Hermes 是 Agent、Session 和工具执行的权威，客户端没有必要复制后端业务层；有限模块足以隔离异步状态所有权并降低调试成本。
- 影响：拆解以清晰和可调试为目标，不以文件数量或理想行数为目标；非关键 corner case 不进入当前结构改造，UI 组件拆分排在业务边界稳定之后。
- 假设：现有 Hermes 协议和产品范围保持不变，客户端继续承担实时语音与 HarmonyOS 生命周期协调。
- 重新评估条件：五个责任域仍无法隔离状态竞态，或后续新增离线业务、多个后端编排等实质性客户端职责。
- 来源：[用户拆解原则](plans/2026-08-12-thin-client-decomposition-principles.md)

## 2026-08-12 - 先拆解核心文件再修复息屏语音

- 背景：`1.1.2` 真机验收显示亮屏长文正常，但息屏长文仍有断连、缺字漏字和破音；语音“重读一次”偶发有效，而消息气泡按钮无效。`SingleAgentController.ets` 约 3636 行，`Index.ets` 约 1822 行，多个核心功能集中在少数文件中，调试和定向修改成本过高。
- 决策：后续先按功能所有权和异步事件边界小步拆解核心文件，再处理息屏 TTS 和消息重读；本轮不直接开发业务修复，不做一次性大重写。
- 依据：当前问题跨越生命周期、后台任务、TTS 分段、音频播放和 UI 入口；没有清晰边界时直接修复容易复制状态、引入竞态并拖慢回归。
- 影响：短期新增结构性工作，息屏和重读修复顺延；长期可在单模块内定位问题、补验证并降低核心控制器变更风险。
- 假设：现有 Hermes 协议、Session 连续性和系统语音主路径保持不变，拆分可以通过逐步提取和每步验证完成。
- 重新评估条件：若拆分本身引入状态漂移、异步竞态或无法改善问题定位，应暂停继续拆分，回到最小可验证边界重新设计。

## 2026-08-12 - 访问口令以可用性优先保存到应用私有 Preferences

- 背景：目标 HarmonyOS 6.1 / API 24 真机上的 HUKS AES-GCM 可完成加密写入，但同一进程立即解密回读失败；用户确认该安全增强不是核心功能，并明确允许明文或简单加密持久化。
- 决策：`GatewayTokenStore` 使用应用私有 Preferences 保存访问口令，写入后同步读回验证；启动时清理不可恢复的旧 HUKS 密文记录，不再让 HUKS 失败阻断连接。
- 依据：真机连续复现 `save complete` 后 `load failed`，而 Preferences 写入、立即读回和强制停止后恢复均已验证；自制可逆“简单加密”不提供有效安全收益。
- 影响：重开无需重复输入口令，但当前版本不提供硬件级静态加密；日志仍只记录记录存在性和阶段，不记录口令内容。
- 重新评估条件：HarmonyOS HUKS 在目标设备上有稳定、可回归的实现范式，或发布合规明确要求硬件级凭据保护。
- 替代：本决策取代下方“2026-08-11 - 访问口令使用 HUKS 密钥加密存储”的当前有效性；旧条目保留为历史。

## 2026-08-12 - 本项目持续授权真机部署与客观冒烟

- 背景：HarmonyOS 开发每轮都需要将签名 HAP 安装到固定真机并拉起应用，逐次重复请求相同授权影响验证连续性。
- 决策：用户对本项目给予持续有效的设备授权；AI 可在后续开发任务中直接检查设备连接、保留数据安装签名 HAP、拉起清单声明的 Ability，并执行包/进程状态和不提交真实业务数据的简单接口状态检查，无需每轮重复询问。
- 依据：上述动作范围固定、结果客观且是 HarmonyOS 构建验证的正常延续；用户已明确说明该授权不是单次授权。
- 影响：此前“真机交互默认由用户操作”的决策在安装、拉起和简单冒烟范围内被本条替代；点击流程、麦克风说话、语音听感、复杂功能正确性、截图验收和视觉美感仍由用户操作并反馈，不得把安装或拉起写成产品验收通过。
- 假设：目标设备、包名和 Ability 与项目清单一致，安装默认保留应用数据，日志和接口输出不包含访问口令或其他敏感信息。
- 重新评估条件：用户明确撤销或缩小授权；目标设备、包名、签名主体或测试动作超出本项目；操作会清除数据、提交真实 Prompt/音频或产生其他显著外部副作用。
- 来源：[用户原始授权](plans/2026-08-12-permanent-device-smoke-authorization.md)

## 2026-08-11 - 网关使用下行应用层心跳与无损恢复

- 背景：真机经公网 Cloudflare / OpenResty 链路约 135 秒出现一次阶段性断线；Hermes 上游协议 ping 不会自动转发到 HarmonyOS，且旧自动恢复复用了会执行 `stopVoice()` 的手动历史恢复路径。
- 决策：Adapter 仅在 `/api/hermes/ws` 每 25 秒向客户端发送 `gateway.heartbeat`；HarmonyOS 收到首个心跳后启用 70 秒看门狗，并在超时后关闭旧 socket、重新鉴权和无损恢复当前 Session。恢复路径不得清空消息、关闭语音输出或重放 Prompt。
- 依据：应用层心跳能穿过现有代理并被客户端直接观测；首心跳后才启用看门狗可兼容旧 Adapter；Session 与语音/播放是独立状态所有权。
- 影响：Adapter 的同一客户端写入必须串行；心跳由网关客户端内部消费；部署时需要同步更新 Adapter 和 HAP 才能获得完整保活能力。
- 假设：公网链路允许 25 秒文本帧通过，70 秒足以容纳调度抖动且能比约 135 秒的代理回收更早发现悬挂。
- 重新评估条件：代理层提供并验证更长的空闲超时或标准 WebSocket ping 可端到端到达 HarmonyOS；或 Hermes 增加正式的客户端保活协议。
- 来源：[用户原始任务](plans/2026-08-11-gateway-heartbeat-and-replay-recovery.md)

## 2026-08-11 - 协议请求使用对话流而非独立卡片

- 背景：审批卡和澄清选项卡会打断语音对话的连续感，并形成额外的移动端操作界面。
- 决策：HarmonyOS 将 `approval.request` 和 `clarify.request` 展示为普通对话内容；用户下一条有效回复仍直接映射到 Hermes `approval.respond` 或 `clarify.respond`，不作为新的 Agent Prompt。
- 依据：保持单一对话主界面，同时不改变 Hermes 对审批和澄清状态的所有权。
- 影响：审批必须继续使用精确允许 / 拒绝词表并默认安全失败；澄清回复需在客户端识别 pending 状态后走专用协议。
- 假设：Hermes 在 pending 状态下接受现有响应方法并继续原任务。
- 重新评估条件：未来明确需要复杂表单、多选或无法通过对话可靠表达的结构化输入。
- 来源：[用户原始任务](plans/2026-08-11-conversational-prompts-and-provider-identity.md)

## 2026-08-11 - 真机交互验收由用户操作

- 背景：HarmonyOS 真机上的点击、语音、听感和视觉反馈需要直接观察，用户操作更快且更直观。
- 决策：AI 负责源码、自动化检查、构建产物、日志点位和复现步骤；真机交互默认由用户操作并反馈结果。
- 依据：避免远程自动操作遮蔽真实界面和声音状态，提高真机调试效率。
- 影响：不能把仅完成构建或安装写成真机验收通过；状态文档需明确区分自动验证与用户真机结论。
- 假设：真机保持连接，用户可在需要时执行简短验证步骤。
- 重新评估条件：用户在具体任务中明确授权或要求 AI 操作真机。
- 来源：[用户原始任务](plans/2026-08-11-conversational-prompts-and-provider-identity.md)

## 2026-08-11 - Agent Catalog 只使用正式服务端契约

- 背景：新版 HarmonyOS 客户端依赖 `/api/agents`，而 `foxi` 曾运行缺少该路由的旧 Adapter，真机因此收到 HTTP 404。
- 决策：服务端必须提供 `/api/agents`；客户端不增加固定 Profile 或其他旧接口降级逻辑。
- 依据：Agent 清单、身份和语音策略属于服务端配置，客户端降级会形成第二套配置来源并掩盖部署版本不一致。
- 影响：客户端在契约缺失时明确报错；发布客户端前必须同步部署和验证 Adapter。
- 假设：项目能够控制正式 Adapter 的版本和发布流程。
- 重新评估条件：未来明确需要兼容无法升级的第三方 Adapter，且形成带版本号的正式兼容协议。
- 来源：[用户原始任务](plans/2026-08-11-server-agent-catalog-contract.md)

## 2026-08-11 - HarmonyOS 是最终移动交付面

- 背景：Web Native 的用途是快速验证 Hermes、语音和跨端协议，不是长期产品交付目标。
- 决策：当前 Web 版本稳定后暂停新增功能，仅保留协议回归和稳定性修复；后续产品能力和体验验收优先投入 HarmonyOS。

## 2026-08-11 - 访问口令使用 HUKS 密钥加密存储

- 背景：HarmonyOS 客户端此前把长期访问口令直接写入 Preferences，无法满足移动端凭据静态存储边界。
- 决策：使用应用作用域 HUKS 密钥执行 AES-256-GCM 加解密，每次写入生成 12 字节随机 nonce；Preferences 只保存版本、nonce 及带 16 字节认证标签的密文。旧明文字段只在安全写入并落盘成功后删除。
- 依据：HUKS 保持密钥材料不进入应用配置，GCM 同时提供机密性和完整性；版本化信封为后续算法迁移保留边界。
- 影响：页面启动和设置保存必须等待异步安全存储；解密或迁移失败时要求用户重新输入，不允许回退读取明文，也不得记录口令内容。
- 假设：目标 HarmonyOS 6.1 / API 24 设备支持当前 HUKS AES-GCM 参数及 CE 存储级别。
- 重新评估条件：平台 HUKS 参数、应用数据迁移策略、设备锁定要求或凭据轮换机制发生变化。

## 2026-08-11 - Gateway 重连只恢复 Session

- 背景：Gateway 断线可能发生在 Prompt 已被 Hermes 接收之后；客户端无法仅凭 socket 关闭判断服务端是否执行过该消息。
- 决策：瞬态网络或 5xx 故障重新获取短期 Cookie 并恢复 `storedSessionId`，绝不在重连路径自动调用 `prompt.submit`；401/403 作为终止鉴权失败停止自动重试。
- 依据：Session 是服务端拥有的连续性边界，自动重放 Prompt 会产生重复任务、重复工具调用或不可逆副作用。
- 影响：断线中的未确认消息可能需要用户根据恢复后的 Session 状态决定是否再次发送，但客户端不会制造重复执行；重连需隔离旧 socket 和旧 HTTP 请求的迟到回调。
- 假设：Hermes `session.resume` 能返回服务端已持久化的最新会话状态。
- 重新评估条件：服务端提供带幂等键的 Prompt 提交与明确的接收确认协议。

## 2026-08-11 - 收音控制词使用四条精确白名单

- 背景：短口令“闭麦”容易被中文 STT 误识别为无关英文片段，宽松接受这些结果会把识别错误放大为真实控制动作。
- 决策：只匹配“关闭话筒”“关闭麦克风”“关闭microphone”“暂停收音”；匹配前统一小写并移除空格、标点和符号，归一化后仍要求整句完全相等。
- 依据：四条口令覆盖已验证的中文表达和一个明确的中英混写结果，同时避免任意英文片段、包含句或模糊近似触发关闭输入。
- 影响：旧口令“闭麦”、`be my`、`in my`、`be mine` 及带其他语义内容的句子不再触发；“停止”继续独立表示中断任务。
- 假设：当前 ASR 主要服务中文连续对话，用户可以通过 UI 麦克风按钮重新开启收音。
- 重新评估条件：真机持续出现新的稳定误识别且能证明不会与普通对话冲突，或产品改为多语言语音控制。
