## 下一开发任务：过程时间线与历史回放闭环（待开发）

状态：2026-08-16 仅完成分析和计划记录，未修改实现代码。既有架构决策见[关键决策记录](decisions.md)中的“思考、工具与状态统一为有序过程时间线”。本任务不扩展 Agent 能力，只让同一执行过程的实时展示、历史回放、布局和计时语义闭环。

### 已确认问题与边界

1. Hermes 持久历史包含 `reasoning_content`、Assistant `tool_calls` 和后续 `role: tool` 结果；重新进入历史后只剩思考内容不是正常降级。
2. 实时过程来自 `thinking.* / tool.*` 事件，历史过程来自 Hermes 消息行；两条输入链路应归一化为同一个 `MessageActivity[]`，并共享排序、合并和渲染规则。
3. 当前历史详情读取失败会退回 `session.resume` 的简化消息，工具记录可能因此消失且没有完整性提示。实际部署的 Adapter 历史详情接口及响应字段仍需在开发开始时核验。
4. 当前动作固定使用标题行和内容行，且只有工具通常带 `duration_s`；这是当前数据模型和渲染方式造成的不一致，不作为最终交互规则。
5. 默认界面每个动作只占一行；长输入、完整结果和错误明细按需展开。摘要不得直接显示令牌、凭据或未经裁剪的大段原始参数。

### 目标结构

```text
Hermes 实时事件 ----> 实时归一化器 --\
                                      > 共享 Activity reducer -> MessageActivity[] -> 单行时间线
Hermes 历史消息 ----> 历史归一化器 --/
```

- `MessageActivity` 继续作为唯一 UI 过程模型，至少包含稳定 `id`、`kind`、`title`、摘要/明细、`state`，并补充可选的开始时间、结束时间和可显示耗时。
- reducer 按到达顺序创建活动；同一 `tool_id/call_id` 的进展和结果只原地更新，不在末尾重复追加。
- 连续思考 delta 只合并到当前运行中的思考段；工具开始、状态变化或回答首字到达时结束当前思考段。工具完成后的新思考必须形成新活动。
- 实时和历史只保留输入适配差异，不维护两套过程 Store，也不在 Adapter 建立第二套会话数据库。

### 计时与展示规则

- 统一展示“客户端观测到的阶段用时”，不把 `ChatMessage.thinking_s` 直接冒充某一段思考耗时；该字段仍只表示整条回答首次出字前的等待指标。
- 运行中动作可按现有页面时钟刷新累计秒数，完成后冻结，避免额外建立高频定时器。
- 工具行摘要格式为“调用 · 工具名 · 结果状态”，思考行摘要使用当前思考内容的首个有效短句；无有效摘要时使用稳定占位，不展示原始 JSON。
- 历史消息时间戳只有在语义明确并可形成前后边界时才参与计算；无法证明准确的历史耗时直接省略。

### 验收场景

1. 发起一轮至少包含两次工具调用的对话，实时记录依次显示思考、调用及结果、再次思考和最终回答。
2. 返回历史列表并重新进入同一 Session，活动数量、顺序、工具名称和成功/失败状态与实时阶段一致。
3. 实时与历史默认均为一动作一行；点击任一工具行可看到经过裁剪和脱敏的输入/结果明细，再次点击收起。
4. 思考和工具在有可靠边界时都显示耗时；缺失历史时间时仅省略该项耗时，不影响其他活动。
5. 人为让历史详情接口失败，正文仍可查看，同时明确显示过程记录不完整；不得静默退回为“只有思考”。
6. 无工具的普通回答、只有工具没有思考文本、工具失败、重复 `tool.complete`、迟到结果和中断任务均不产生重复活动或错序。

本阶段停止语音体验增强和局部补丁，先完成底座收敛。

## 核心约束

1. 同一 Profile 切换历史 Session 不停止健康的 Capturer 和 ASR。
2. Session/Profile/后端切换、完整停止和释放统一使用 Runtime `epoch`。
3. 本地和远端 ASR 共用唯一 Capturer。
4. 正文、重读、协议播报和提示音进入唯一 PlaybackQueue。
5. 后台保护保存录音、播放两个独立 demand，平台模式由真机能力门选定。
6. screen/background 事件只作诊断，不直接 stop/start 音频资源。
7. 恢复必须有限，耗尽后进入明确失败态。
8. 组件不得直接写共享 UI 音频状态或全局错误字符串。
9. mailbox 只串行 reducer，不等待平台 Promise；异步 effect 的结果携带 epoch 回投。

## 下一步

下一步只进行一次集中真机验收。先安装本轮签名 HAP 并清理日志，再严格按下表顺序执行；任一失败都保留完整日志、屏幕状态、音频路由和发生步骤，不在现场改代码后继续混测。

| 顺序 | 真机场景 | 操作 | 通过证据 |
| --- | --- | --- | --- |
| D1 | 旧会话开麦（已通过） | 新会话说话并收到回复，往返两个历史 Session 后继续说话 | 每次都能收到新 final；没有重复 Capturer、假“监听中”或旧 Session 回调 |
| D2 | 固定录音租约下的息屏输入 | 亮屏开麦，息屏至少 2 分钟后继续说话 | 后台始终为 recording；PCM/ASR 持续或有限恢复；不出现 `system error` |
| D3 | 系统 TTS 息屏输出 | 开麦触发长回复，在播报中息屏至少 60 秒后解锁 | 毫秒级伪完成不推进队列；不漏段；若 CoreSpeech 暂停，解锁后从完整当前段恢复 |
| D4 | 双讲与恢复 | 正文播报中说话，补充完成后等待正文恢复，再继续说话 | 播报及时暂停；从完整短段恢复，允许少量重复但不吞字；输入不被播报永久关闭 |
| D5 | 四类 cue | 分别触发收到、思考、停止、错误提示 | 提示只响一次且不与正文重叠；停止/错误优先级正确；cue 完成不推进旧 job |
| D6 | 路由变化 | 播放和录音期间插拔耳机，并切换扬声器/耳机 | 路由变化后输入输出恢复；Renderer、AudioSession 恢复不会无限重试 |
| D7 | 生命周期 | 前后台往返、锁屏/解锁后退出，再重新启动 | 音频链路可继续工作；退出释放资源；冷启动无旧回调或旧任务复活 |
| D8 | 恢复耗尽 | 在可控条件下造成录音或播放连续失活 | 60 秒最多 3 次恢复；达到上限进入终态，手动重启后可建立新 epoch |

若 D2 失败，再与会话级固定 `AUDIO_PLAYBACK` 做最小对比；若 D2 通过但 D3 只能做到“不丢文本、解锁恢复”而不能息屏连续播放，则确认 CoreSpeech 平台边界，后台连续播报改由远端 PCM 承担，不再让系统 TTS 队列猜测播放进度。
