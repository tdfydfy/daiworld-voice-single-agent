- 本次来源：[恢复旧版已验证的息屏播放路径](plans/2026-08-13-restore-proven-screen-off-playback.md)，长期范围仍以[用户旅程北极星](plans/2026-08-13-user-journey-north-star.md)为准。

- 阶段目标：恢复已验证的专用后台模式切换，同时消除虚假采集状态和陈旧异步回调，使四段旅程共享一套可观测、可恢复的输入输出基础。

## 0. 固定行为契约和可观测性

- [ ] 建立四段旅程的状态转换测试
  - 目标：先固定产品正确性，再迁移资源所有权。
  - 覆盖：普通输入最多提交一次；忙碌时补充保持顺序；说话只暂停播报；关闭/打开话筒只切消息路由；亮屏/息屏不切业务路径；停止/退出后旧 ready、TTS、socket 回调不能推进新状态。
  - 方案摘要：围绕现有 `VoiceInputCoordinator`、`VoiceOutputCoordinator`、`HermesRuntime` 和控制器命令门补可执行行为测试；`S00-S21` 仅补充平台故障序列。
  - 验收条件：测试至少能对当前 recording/playback 异步切换、关闭话筒停止采集等目标差距给出失败证据；后续每个切片以相同测试回归。
  - 当前结果：已增加生产 `AudioContinuityState` 和 `CaptureRecoveryState` 的 9 个可执行用例，覆盖录音到播放的 stop/start 顺序、播放结束恢复录音、启动中意图抢占、陈旧代次隔离、单次恢复、三次上限、PCM 重置预算和显式停止；输入路由、Agent 等待、输出与退出行为按后续阶段继续补齐。

- [ ] 统一关键日志关联字段
  - 目标：一次日志可还原 `journey phase -> demand -> lease -> capture/asr -> task -> playback job` 的顺序。
  - 方案摘要：复用代际机制，统一记录 lease generation、capture generation、ASR utterance、Hermes request、playback job/chunk；不记录用户正文或凭据。
  - 验收条件：能区分用户意图、资源状态和健康证据，能判断是未启动、恢复中、已失活还是正常运行。

## 1. 持续运行底座

- [x] 恢复录播专用后台模式和 ready 门
  - 对应承诺：四段旅程及环境变化都不能制造录播空窗。
  - 方案摘要：`AudioContinuityCoordinator` 根据控制器意图串行切换专用模式；播放排队或发声时优先 `AUDIO_PLAYBACK`，否则持续收音时使用 `AUDIO_RECORDING`。Capturer 与首段 TTS 都等待对应模式 ready。
  - 验收条件：系统 TTS 只在播放模式 ready 后启动；播完或用户开口后恢复录音；停止旧模式遇到 `9800005` 按已停止收敛；失败有明确状态。
  - 风险：模式切换需要一次 stop/start，但这是 `1.1.2/1.2.1` 已通过目标真机息屏验收的路径；仍需确认当前系统和采集恢复改造没有引入新的空窗。
  - 实际结果：组合租约在 `1.2.3` 虽保持存活，却未阻止 CoreSpeech `OnPageHide`；`1.2.5` 已恢复旧版专用模式和可等待的串行切换，同时保留 `9800005` 幂等处理。静态、ArkTS 和签名构建已通过，息屏听感待真机门。

- [x] 建立唯一 Capturer 的真实健康与有限恢复
  - 对应承诺：完整链路启动后持续听见用户，局部故障只恢复输入域。
  - 方案摘要：新增 `CaptureSupervisor`；`PcmCapture` 上报 `stateChange`、`audioInterrupt`、PCM 心跳和 AudioSession 恢复；非 RUNNING 或约 2 秒无 PCM 时串行重建；本地/远端 ASR 各自接入相同监督契约，且仍只启动当前选中后端的一个 Capturer。
  - 验收条件：息屏、锁屏/解锁、短暂中断和路由变化后 PCM 自动恢复；不出现并发 Capturer；恢复耗尽后停止显示“监听中”，保留已确认文本并提供手动重启入口。
  - 风险：恢复期间需保留有限 pre-roll，并避免把同一句话拆成重复 Prompt。
  - 实际结果：恢复采用 `100 / 500 / 1500 ms` 三次预算、单任务串行和 generation 隔离；恢复中保留识别会话与已确认转写，耗尽后明确停止麦克风意图。真机中断、无 PCM 和息屏恢复待验证。

- [ ] 分离系统 ASR/TTS 请求所有权并补全 generation
  - 对应承诺：输入恢复不影响播报，旧回调不能跨任务推进状态。
  - 方案摘要：从 `SystemSpeechService` 逐步拆出 `SystemAsrEngine` 和 `SystemTtsPlayer`，先保持现有后端策略；所有 session/request 回调校验 generation。
  - 验收条件：ASR 轮换、停止、Session/Agent 切换和 TTS 新旧请求交错时，旧回调只被记录和忽略。

## 2. 发起/补充与输入路由

- [ ] 落地本地系统指令门与两种消息路由
  - 目标：`关闭话筒`只切到仅系统指令模式，采集和 ASR 不重启；`打开话筒`恢复普通消息提交。
  - 方案摘要：final 先做精确整句指令匹配；普通模式允许普通内容进入收句/提交，系统指令模式只接受“停止任务 / 打开话筒 / 退出软件”，其余结果本地丢弃。
  - 验收条件：被丢弃内容不建气泡、不响收到提示、不访问 Adapter/Hermes；每次冷启动首次完整链路仍需用户手动开启；UI 明确显示“仅响应系统指令”。

- [ ] 统一收句、提交和接受状态
  - 目标：同一句话跨 ASR Session、短暂中断或 1.8 秒自然停顿时最多形成一次 Agent 输入。
  - 方案摘要：用统一 utterance 缓冲承接 local/remote final；区分“已收句 / 提交中 / 已接受或已排队 / 未提交”；收到提示音只表达有效收句，不掩盖提交失败。
  - 验收条件：补充可在等待和播报期间进入；断线或超时后保留未确认内容，不自动重提；纯符号、空 final 和回音不提交。

## 3. Agent 等待与断线对账

- [ ] 以 Hermes 作为任务和排队状态权威
  - 目标：用户看到的已接受、已排队、处理中、审批/澄清和完成状态都有服务端证据。
  - 方案摘要：复用现有 Session 无损恢复；梳理 `prompt.submit(queued=true)` 的确认边界；恢复时只对账 Session 和任务结果，不重放 Prompt；本地音频状态独立保留。
  - 验收条件：等待期间多次补充保持顺序；Gateway 瞬态断线不重复任务、不清消息、不停止健康音频；未确认状态不冒充成功。

- [ ] 收敛等待期提醒
  - 目标：收到提示和思考呼吸音准确表达状态，不改变任务或音频资源。
  - 验收条件：呼吸音只在 Agent 活跃且无人说话、无正文、无审批/澄清、无错误时出现；所有终止路径稳定停止。

## 4. 唯一可听输出

- [ ] 建立公共 `SpeechPlaybackJob`、分段器和队列
  - 目标：新回复、历史重读、协议播报和四类提醒只有一个可听输出所有者。
  - 方案摘要：拆出 `SpeechSegmenter` 与 `SpeechPlaybackQueue`；统一优先级为停止/错误 > 用户讲话静默 > 正文/重读 > 收到提示 > 思考呼吸；所有 job/chunk 使用 generation 隔离。
  - 验收条件：任一时刻只有一个播放器推进队列；正文与重读共用分段；收到提示不切断正文；停止清空后只响一次停止提示；错误不重复轰炸。

- [ ] 收紧系统 TTS 完成和暂停恢复语义
  - 目标：用户开口时暂停，普通补充提交后从可靠短段检查点恢复；允许有限重复，不允许吞字。
  - 方案摘要：目标真机不返回可用的本地 TTS PCM，因此恢复 CoreSpeech 系统播放器；在调用 `engine.speak()` 前确保专用 `AUDIO_PLAYBACK` 后台任务 ready，并以 `onComplete(type=1)` 推进短段队列。
  - 验收条件：亮屏/息屏中途切换、说话暂停、路由变化和陈旧回调均不跳过后续内容。
  - 当前结果：`1.2.4` 真机确认即使显式请求 `audioType: pcm`，CoreSpeech 仍不回调 `onData`，应用 PCM 接管在目标设备上不可行。`1.2.5` 已恢复 `1.1.2/1.2.1` 的系统播放器，并恢复播放优先的专用后台模式；自动化、ArkTS 和签名构建通过，息屏听感待真机门。

- [x] 验证并撤销 CoreSpeech PCM 自管播放
  - 进入条件：组合租约、采集恢复和严格 request 代际已在真机生效，系统 TTS 仍出现 `onComplete` 正常但听感缺字、漏句或跳段。
  - 实际结果：目标真机整轮没有 `SpeakListener.onData`；显式请求 PCM 后仍只得到完成状态并报“本地 TTS 未返回 PCM 音频流”，该方案已被真机证伪并从本地 TTS 路径移除。
  - 后续边界：远端 TTS 继续使用 `PcmPlayer` 和 drain；本地 CoreSpeech 不再依赖 PCM 回调，除非后续系统版本在目标设备上提供可复现的真实 PCM 数据。

## 5. 停止、开闭话筒与退出

- [ ] 实现 `停止任务` 的完整作用域
  - 方案摘要：UI 按钮和精确语音指令共用命令；先停止正文、重读、待播、提醒和思考音，再请求等价 Hermes `/stop` 的当前任务及全部排队任务清理；输入链路和消息路由保持不变。
  - 验收条件：无任务时不创建新任务；服务端未确认时显示“状态待确认”；确认后只响一次停止提示；重连不会复活或重提已取消任务。
  - 待确认：当前 `session.interrupt` 是否能原子清理 Hermes 排队任务；不足时需要服务端正式契约，不能用客户端假状态补齐。

- [ ] 实现统一退出释放
  - 方案摘要：按 Output -> Input -> Background -> Runtime 顺序释放正文/提醒、Capturer/ASR、AudioSession/后台任务、Gateway/定时器/队列，最后终止 UIAbility；默认不隐式停止远端任务。
  - 验收条件：退出后无 Capturer、ASR、播放器、AudioSession、后台任务、socket 或重连定时器；局部释放失败仍继续其余清理；下次冷启动不自动开启完整话筒链路。
  - 待确认：HarmonyOS API 24 主动终止 UIAbility 的稳定入口和异常回退行为。

## 6. 完整旅程真机验收

- [ ] 自动化回归门
  - 覆盖：四段业务转换、录播专用模式切换、Capturer 失活/中断/无 PCM、ASR Session 轮换、TTS 陈旧回调、Gateway 断线、停止/退出资源清理。
  - 通过标准：旧 generation 不推进状态；恢复有上限；局部失败不连带清空其他责任域；Web 协议回归保持通过。
  - 当前结果：2026-08-13 已通过 Node 28 项、Python 27 项、32 个 ETS 静态契约、ArkTS 类型检查和签名构建；后续阶段仍需继续扩展输入路由、输出队列和退出序列测试。

- [ ] HarmonyOS 真机矩阵
  - 主循环：发起、等待、播报、播报中补充、连续补充、停止任务、关闭/打开话筒、退出软件。
  - 环境：亮屏开始后息屏、息屏后开始播报、前后台往返、锁屏/解锁。
  - 持续性：至少 5 分钟连续采集与 ASR、单句跨识别 Session、长回复、新消息/历史重读/四类提醒。
  - 路由：系统原生附件优先；输出按钮任何时候都可打开 `voice_call` 原生设备面板，由用户自由选择当前可用的耳机、听筒或扬声器；覆盖自动播报、气泡重读和远端播放的插拔与手动覆盖。
  - 通过标准：无播放中断、爆破音、明显卡顿、缺字、漏段、重复提交或重复任务；收音意图开启时采集健康有证据，异常后能恢复；无 `6800301`、后台租约空窗或无限重试。

## 暂不进入当前关键路径

- 连续 ASR 1.8 秒停顿的体感微调：代码已有，核心旅程可靠性通过后真机验收。
- 审批/澄清快速应答、动态 Agent 与模型切换：保留现有行为并做回归，不在本轮重构协议。
- UI 密度和视觉细节：仅修复阻塞旅程验收的状态文案或入口，不做独立改版。
- Web Native 新功能：继续只承担协议回归和稳定性修复。
- 通用事件总线、Service Locator、目录大迁移或按方法拆文件：不在范围内。

## 交付纪律

1. 每次只跨过一个完成门：行为保护 -> 实现 -> 静态/类型/单元验证 -> 签名 HAP -> 必要真机验收。
2. 每个代码任务必须标明它修复的用户环节或跨环节承诺；无法建立对应关系的任务不进入当前 P0。
3. 后台模式和服务端 `/stop` 扩展必须由明确证据触发，不提前扩大实现范围；CoreSpeech PCM 已被真机证伪，除非目标设备后续稳定返回数据，否则不再恢复。
4. 真机安装、拉起和客观状态检查沿用既有授权；语音听感、复杂交互和视觉结论仍由用户操作验收。
