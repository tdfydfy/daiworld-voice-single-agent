## R1：系统控制契约闭环

当前状态：`1.2.14 (1020014)` 的退出、停止和话筒控制已经通过用户真机验收。按用户产品判断，前端停止即完成客户端职责，真实 Hermes 全队列语义不再阻塞发布；技术上仍保持“不声称服务端队列已清空”的准确状态表达。

### C0：可选的非阻塞取证

当前客户端调用 `session.interrupt`，现有仓库能证明“请求已发送并清理本地输出”，但不承诺 Hermes 同时清空 `queued:true` 任务。探针工具继续保留，只有后续确实需要诊断后端队列时才在受控 Session 执行，不影响前端交付。

- 若 `session.interrupt` 已清空当前及全部队列：固定为集成测试，客户端只补准确的成功/失败状态。
- 若它只中断当前任务：查明 Hermes 官方 `/stop` 等价入口或最小 Adapter 契约，不在客户端伪造队列已取消。
- 请求无确认或断线时：本地先停止，但 UI 只能显示“任务/队列状态待确认”，恢复连接后对账，不能声称服务端已全部停止。

### C1：实现精确“退出软件”

将“退出软件”加入本地精确系统指令，普通对话和仅系统口令模式都可执行；包含额外语义的句子不得触发。执行顺序沿用现有幂等 `dispose()`：

1. 冻结新提交、自动重连和迟到回调。
2. 依次释放可听输出、采集/ASR、后台持续任务、系统语音和网络连接，每步保持有限超时。
3. 资源释放完成或超时后，调用 HarmonyOS 支持的 Ability 结束入口。
4. 默认不向 Hermes 发送停止远端任务；下次启动必须建立新的 Runtime epoch，旧任务不得在客户端复活。

页面帮助同步补充第四条口令，并明确“退出本地应用不等于停止远端 Agent 任务”。

### C2：控制矩阵验收

| 编号 | 场景 | 通过证据 |
| --- | --- | --- |
| C2-1 | 普通模式说“退出软件” | 应用结束，本地音频、后台任务和连接释放；无自动重连 |
| C2-2 | 关闭话筒后说普通内容，再说“退出软件” | 普通内容不提交；退出口令仍可执行 |
| C2-3 | 说“退出软件后提醒我”等包含句 | 作为普通内容处理，不触发退出 |
| C2-4 | 运行中任务和两个排队任务后说“停止任务” | 当前及排队任务按 C0 已确认契约停止；话筒路由模式不变 |
| C2-5 | 停止或退出过程中断网/出现平台释放错误 | 状态不伪装成功；释放继续有限收敛；旧连接和回调不复活 |
| C2-6 | 退出后重新启动 | 只建立一个新采集链和新 Runtime epoch，无旧播放、旧回调或旧后台任务 |

## R2：行为回归与发布门

现有 `verify.mjs` 和部分 Node 测试仍以源码正则为主。控制契约实现时优先把纯状态逻辑提取为可执行测试，静态守卫只保留 ArkTS 平台绑定和资源声明：

- 输入路由：`conversation / commands_only / off` 的转移、精确口令、普通内容丢弃和协议回复优先级。
- 停止任务：本地输出清理、pending 请求清理、服务端确认/待确认、重复停止和迟到事件隔离。
- 退出软件：dispose 幂等、释放顺序、单步超时、禁止重连和 Ability 结束回调。
- Adapter/Hermes：真实停止契约 fixture，覆盖运行中和多个排队任务。

固定验证门：

```powershell
node --test tests/*.test.js

node clients/harmony/scripts/verify.mjs
hvigorw assembleHap --mode module -p product=default -p buildMode=debug

```

自动化、构建和本轮真机产品验收均已通过。安装、版本、Ability 和进程检查只算客观冒烟；用户操作验收是独立证据。C2-4 中的服务端队列结果仍以 C0 为准。
